The OpenIM Android SDK's `SignalingManager` provides the signaling pipeline required to initiate, accept, reject, cancel, and hang up calls, query room states, and synchronize call participants. It orchestrates call metadata, participant rosters, and call lifecycles, but does not capture camera frames, process audio streams, or render video views.

Pass the `roomID`, `token`, and `liveURL` returned by the SDK to your chosen WebRTC or LiveKit media engine. Your application handles Android runtime permissions, audio routing, media tracks, network adaptation, and calling UI state.

## Calling lifecycle

1. The caller initiates a call using [Start a single call](/sdk/android/calling/managing-calls/start-single-call) or [Start a group call](/sdk/android/calling/managing-calls/start-group-call).
2. The callee receives an incoming invitation event and accepts or rejects the call.
3. The answering party calls [Accept a call](/sdk/android/calling/managing-calls/accept-call), and both sides connect to LiveKit or WebRTC using room credentials returned by the server.
4. Active screens render participant lists, published tracks, and custom business signals during the call.
5. Before connection, the caller can [Cancel a call invitation](/sdk/android/calling/managing-calls/cancel-call); after connection, any participant can [Hang up a call](/sdk/android/calling/managing-calls/hang-up-call).

## Core data structures

| Structure | Description |
| --- | --- |
| `SignalingInvitationInfo` | Inviter, invitees, group ID, room ID, media type, timeout, session type, and custom extension payload. |
| `SignalingInfo` | Current operator, complete invitation data received in events, participant profiles, and optional offline push details. |
| `SignalingCertificate` | `roomID`, `token`, `liveURL`, and busy user lists returned by OpenIMServer. |
| `RoomCallingInfo` | Room details, active invitation, participant roster, group metadata, and access credentials queried by group ID. |

Use `customData` and custom signaling to exchange lightweight, transient session negotiation data. Do not use signaling channels for bulk file transfers or persistent database storage.

## State updates and event ownership

Distinguish clearly between asynchronous API callbacks and real-time signaling events. An API success callback indicates that the server accepted the signaling request; participant state transitions are delivered asynchronously through event listeners.

For the centralized listener handling invitation lifecycles, room entries, exits, hang-ups, and stream updates, see [Handle call events](/sdk/android/calling/managing-calls/handle-call-events). For application-specific signals, see [Send a custom signal](/sdk/android/calling/sending-custom-signals/send-a-custom-signal).

The global primary key for call state is `roomID`; individual participant state is keyed by `roomID` combined with `userID`. When recovering after app restarts or network disconnections, query room APIs to calibrate local state.
