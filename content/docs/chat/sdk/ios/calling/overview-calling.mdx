The OpenIM iOS SDK provides signaling APIs to initiate, accept, reject, cancel, and hang up call invitations, query room status, and synchronize participant states. The SDK manages invitation lifecycles and room membership coordination; it does not capture camera feeds, play audio streams, or render video canvas views.

Your application passes credentials returned by the SDK (`roomID`, `token`, and `liveURL`) to your chosen WebRTC or RTC media engine. The application layer handles system camera and microphone permissions, audio session management, media tracks, network adaptability, and UI rendering.

## Call workflow

1. Invoke [Start a one-to-one call](/sdk/ios/calling/managing-calls/start-single-call) to invite a single user, or invoke [Start a group call](/sdk/ios/calling/managing-calls/start-group-call) for multi-party group calls.
2. The invitee extracts `OIMSignalingInfo` from the incoming invitation callback and chooses to accept or reject the call.
3. Upon acceptance via [Accept a call](/sdk/ios/calling/managing-calls/accept-call), both caller and callee use the returned room credentials to join the media channel.
4. During an active call, track member join/leave events, stream state changes, and custom signaling data via delegates.
5. The initiator can [Cancel a call invitation](/sdk/ios/calling/managing-calls/cancel-call) before connection, and any participant can [Hang up a call](/sdk/ios/calling/managing-calls/hang-up-call) once connected.

## Core data structures

| Structure | Description |
| --- | --- |
| `OIMInvitationInfo` | Details invitee list, group ID, room ID, media type (`audio` or `video`), timeout duration, and session type. |
| `OIMSignalingInfo` | Encapsulates caller identity, invitation parameters, and offline APNs notification payloads. |
| `OIMInvitationResultInfo` | Delivers the server-assigned `roomID`, authentication `token`, `liveURL`, and busy user list. |
| `OIMParticipantConnectedInfo` | Captures active room status, inviter details, and currently connected participants for a group room. |

Custom signals transmit lightweight, transient negotiation payloads during a call session. Do not use custom signals for persistent storage or bulk data transfer.

## State synchronization and event boundaries

Write actions such as initiating, accepting, rejecting, cancelling, or hanging up require handling both completion callbacks and signaling delegate events. Completion callbacks confirm that OpenIMServer processed the request. Delegate callbacks notify other participants and linked multi-terminal devices of state transitions; they represent distinct asynchronous milestones.

Listen for the full invitation lifecycle, participant connection events, hangup triggers, and stream changes in [Handle call events](/sdk/ios/calling/managing-calls/handle-call-events). For transient signaling, refer to [Send a custom signal](/sdk/ios/calling/sending-custom-signals/send-a-custom-signal).

Merge call session state using `roomID` as the primary key, and key participant states with `userID`. When the application relaunches with unresolved invitations, recover state via [Restore a pending invitation](/sdk/ios/calling/retrieving-call-information/restore-pending-invitation). To inspect an ongoing group call room, invoke [Query a group call room](/sdk/ios/calling/retrieving-call-information/get-room-by-group-id).
